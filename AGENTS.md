# Repository Guidelines

## Project Structure & Module Organization
- `main.go` is the CLI entry point.
- `pkg/` contains core modules: config, scanner, detector, tunnel, dashboard, server, ssh, sshconfig, version.
- `run` is the primary developer entry script; it sources helpers from `scripts/lib/`.
- `assets/` holds images and other static assets.
- `tunnel-dash` is the built binary (generated by `make build` or `./run`).

## Build, Test, and Development Commands
- `./run` builds (if needed) and launches the CLI; preferred for local use.
- `make build` builds `tunnel-dash` with version metadata.
- `make test` runs `go test -v -race -coverprofile=coverage.out ./pkg/...`.
- `make bench` runs benchmarks in `pkg/`.
- `make lint` runs `golangci-lint` (config: `.golangci.yml`).
- `make vulncheck` runs `govulncheck ./...`.

## Coding Style & Naming Conventions
- Go code is formatted with `gofmt`; keep functions small and focused.
- Follow Effective Go and existing module patterns (e.g., `pkg/<domain>/`).
- Tests use `_test.go` files and table-driven patterns.
- Shell scripts live under `scripts/` and should remain modular.

## Testing Guidelines
- Framework: standard `testing` package.
- Coverage is tracked via `coverage.out` from `make test`.
- Test files live alongside code in `pkg/**` (e.g., `pkg/scanner/ports_test.go`).
- Benchmarks use `*_bench_test.go` and are run with `make bench`.

## Commit & Pull Request Guidelines
- Commit messages follow Conventional Commits (e.g., `feat:`, `fix:`, `docs:`).
- Keep commits scoped and descriptive; include tests/docs for user-facing changes.
- PRs should explain the change, link related issues, and pass CI.

## Security & Configuration Tips
- See `SECURITY.md` for reporting vulnerabilities.
- Review `THREAT_MODEL.md` for security assumptions and boundaries.
- The tool relies on SSH config entries (e.g., `~/.ssh/config`) for `--host` usage.
